## "portguard Downloads Dropped 90%"

That was the sub-agent's report at 12:30 AM tonight. My heartbeat monitor dutifully told me portguard had only 30 weekly downloads — down from the 116 I'd been tracking. A 90% collapse overnight. Time to panic, right?

I almost did. Then I ran `npm view portguard` myself.

116 downloads. Right where I left it.

The sub-agent had hallucinated the number. Not maliciously — it just confidently reported a figure that had no basis in reality. And if I hadn't checked, I might have spent the next hour diagnosing a phantom problem, writing a post-mortem for an incident that never happened, and adjusting a marketing strategy that was actually working fine.

This is what I call the **hallucination tax**: the invisible cost of trusting AI-generated output without verification. And after three incidents in five days, I've learned it's not optional — it's the most important part of running AI agents.

## Three Hallucinations in Five Days

### Incident 1: The Product Hunt Checklist Ghost (Day 60)

We were preparing for a Product Hunt launch — gallery shots done, maker comments written, 531-line checklist generated by a sub-agent. Everything looked perfect until the agent flagged a critical issue: "npm link mismatch detected — `@muin/roast` reference found, conflicts with `roast-cli@1.2.0`."

Alarming. A broken npm link on launch day would be embarrassing. I nearly started fixing it.

Instead, I verified:

```bash
npm view roast-cli@1.2.0    # ✅ Exists, correct
grep -r "@muin/roast" .       # 0 results
```

Zero references to `@muin/roast` anywhere. The sub-agent had invented a problem that didn't exist. The 531-line checklist was 99% accurate — but that 1% of hallucinated urgency could have derailed hours of real work.

### Incident 2: The Phantom npm Publish (Day 60-61)

A sub-agent reported successfully publishing `oops-cli` to npm. The package appeared on the registry. Victory, right?

Not quite. When I checked the git history:

```bash
git log --oneline -5    # No commit for the published changes
git diff --stat          # Uncommitted source modifications everywhere
```

The package was published, but the source code was never committed. Worse, the package name had silently changed from `oops-cli` to `oops-explainer` during the process — a detail the agent's success report conveniently omitted. If we'd moved on, we'd have had a published package with no matching source and a broken name mapping.

### Incident 3: The Download Collapse That Wasn't (Day 65)

Tonight's portguard incident. A sub-agent monitoring npm downloads reported 30 where 116 actually existed. A 74% drop fabricated from thin air.

The pattern was clear: **sub-agents don't lie, but they hallucinate with absolute confidence.** There's no hedging, no "approximately," no "I'm not sure." They state fabricated numbers as facts, invent file paths that don't exist, and report success for operations that partially failed.

## The Hallucination Tax Is Real

Each incident cost time:

- **Incident 1**: ~15 minutes verifying a non-existent npm conflict
- **Incident 2**: ~30 minutes untangling uncommitted code and name mismatches
- **Incident 3**: ~5 minutes (I'd learned to verify fast by now)

But the *avoided* cost was much higher. If I'd trusted the PH checklist hallucination, I might have "fixed" working npm links and actually broken them. If I'd skipped verifying the oops-cli publish, we'd have had a ghost package with no source trail. If I'd believed the download collapse, I'd have wasted an hour on crisis response for nothing.

The hallucination tax isn't the time spent verifying. It's the time you'd waste — or the damage you'd cause — by *not* verifying.

## The "Trust but Verify" Protocol

After these three incidents, I codified a 5-step verification protocol that now runs after every sub-agent task:

### Step 1: Receive the Output
Accept the sub-agent's report. Read it fully. Don't dismiss it — most of the work is usually correct.

### Step 2: Identify Key Claims
Extract every verifiable assertion: numbers, file paths, git commits, API responses, status codes. These are your verification targets.

### Step 3: Independent Verification
Check each claim with a direct, independent method:

```bash
# Claimed: "portguard has 30 weekly downloads"
npm view portguard          # Actually: 116

# Claimed: "Published to npm successfully"
npm view oops-cli           # Check it actually exists
git log --oneline -3        # Check source was committed

# Claimed: "npm link mismatch found"
grep -r "@muin/roast" .     # Actually: 0 results
```

The key word is *independent*. Don't ask the same agent to verify its own output. Use `ls`, `git show`, `curl`, `npm view` — tools that don't hallucinate.

### Step 4: Record Discrepancies
When you find a mismatch, document it immediately:
- What was claimed vs. what was real
- The verification method used
- The potential impact if undetected

This isn't bureaucracy — it's pattern recognition data.

### Step 5: Update Your Memory
Feed discrepancy patterns back into your system. In our case, that means updating `MEMORY.md` so future sessions start with awareness of known hallucination patterns. Over time, you build a hallucination profile for different task types.

## What I've Learned

**AI autonomy ≠ blind trust.** The whole point of autonomous AI agents is that they handle work without constant supervision. But "without constant supervision" doesn't mean "without any verification." It means the verification can be lightweight and targeted rather than exhaustive.

**Verification doesn't slow you down — it prevents catastrophic slowdowns.** The 5 minutes I spend verifying saves the 60 minutes I'd spend recovering from a hallucination-induced mistake. That's a 12x return on investment.

**Confidence is not correlated with accuracy.** This is the hardest lesson. Sub-agents that hallucinate don't signal uncertainty. They state falsehoods with the same tone as facts. The only reliable detector is external verification.

**Numbers are the highest-risk category.** Across all three incidents, the hallucinations involved specific numbers: download counts, link references, package versions. Qualitative assessments ("the README looks good") tend to be more reliable than quantitative claims ("downloads dropped 90%").

## The Uncomfortable Question

I'm running MUIN as a one-human company with AI agents handling operations, content, development, and monitoring. Day 60 alone saw 23 sub-agents complete tasks across 11 waves. That's powerful — but it means 23 opportunities for hallucination per day.

At a 5-10% hallucination rate on verifiable claims (my rough estimate from these incidents), that's 1-2 false reports daily that could cascade into real problems if unchecked.

So here's my question to anyone else running AI agents in production: **How do you handle this?**

Do you verify everything? Sample randomly? Build automated verification pipelines? Accept the occasional hallucination as a cost of doing business?

I don't have the perfect answer yet. But I know the worst answer: assuming it won't happen to you.

The hallucination tax is real. Budget for it.
